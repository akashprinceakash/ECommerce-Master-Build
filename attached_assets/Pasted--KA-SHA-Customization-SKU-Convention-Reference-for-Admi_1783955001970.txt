## 1. Decoding the existing Men's T-Shirt SKUs

Before extending the pattern, here's what your three live examples actually encode:

| SKU | Style Code | Garment Type Letter | Customization Type | Variant |
|---|---|---|---|---|
| `KS1001B-BP` | 1001 | `B` = Basic Tee | Pattern (pick-a-pattern) | `BP` = pattern/colorway id |
| `KS1001B-black` | 1001 | `B` = Basic Tee | Pattern | `black` = colorway id |
| `KS1000BGP001` | 1000 | `B` = Basic Tee | Print (all-over) | `GP001` = graphic print #001 |
| `KS1000BPINK` | 1000 | `B` = Basic Tee | Solid | `PINK` = color name |

So the structure is: **`[Prefix][StyleNo][TypeLetter][Separator][Variant]`**
- `KS` = Men's / `KL` = Women's (already true in your doc — men's are all `KS…`, women's are all `KL…`)
- `TypeLetter` tells the 3D pipeline which garment mesh/zone-map to load: `B` = Top/Tee, `F` = Bottom (Pant/Short), `D` = Dress, `G` = Skort
- One inconsistency worth fixing with Raj: Pattern uses a hyphen (`-BP`), Print/Solid don't (`GP001`, `PINK`). I've kept everything **hyphenated** below so the developer can reliably `split('-')` instead of writing per-type parsing logic. Suggest asking Raj to standardize the existing men's tee entries the same way (`KS1000B-GP001`, `KS1000B-PINK`) — low-risk cleanup, one-time.

**Recommended universal parser logic for developer:**
```
[PREFIX][STYLE#][TYPE]-[VARIANT_TYPE]-[VARIANT_VALUE]
KS1000B-PRT-001   → Men, Style 1000, Top, Print, print #001
KS1000B-SLD-BLK   → Men, Style 1000, Top, Solid, black
KS1001B-PAT-BLK   → Men, Style 1001, Top, Pattern, black colorway
```
`VARIANT_TYPE` (`PRT`/`SLD`/`PAT`) lets the frontend switch customization UI (print grid vs. color picker vs. pattern picker) off one SKU field, instead of inferring type from string shape.

### Skort — Style KL1015G (two-zone garment, needs a compound SKU)
This one has **two independently customizable zones** — solid belt + printed body — so a single flat SKU needs both values encoded:

`KL1015G-SLD-<BELT_COLOR>_PRT-<PRINT_SEQ>`

Example: `KL1015G-SLD-BLK_PRT-004` → black belt + print #004 on the body.

Developer note: split on `_` first to get the two zone-assignments, then split each half on `-` as usual. This keeps it a single admin-facing SKU field rather than needing two separate DB columns, but still machine-parseable.

### Dress — Style KL1014D (solid only, single control drives two mesh parts)
Only the collar is customizable, and the shorts underneath auto-match the collar color — so this only ever needs the Solid type, and the *same* variant value drives both the collar material and the shorts material in the 3D scene.

`KL1014D-SLD-<COLLAR_COLOR>`

Example: `KL1014D-SLD-BLK` → collar = black, shorts = black (applied to both meshes from one SKU value).

## 7. Fixing the hardcoded pattern-color problem (`-BP` doesn't scale)

Right now `KS1001B-BP` almost certainly works because somewhere in the code there's a literal check for the string `"BP"` that resolves to "apply black to zone 1, pink to zone 2." That means every new colorway — Blue+Purple, Blue+Black, a single-color pattern, etc. — requires a **new hardcoded case**. Same class of bug as the mis-priced credit package: fine for the first two SKUs Raj typed in, silently broken for the third.

**The fix:** stop treating the suffix as an opaque code (`BP`) and start treating it as an **ordered, comma-separated list of canonical color tokens**, resolved through the same color lookup table Solid already uses, then applied positionally onto however many recolor zones that pattern group defines.

New SKU shape:
```
KS1001B-PAT-BLK,PNK     → 2-zone pattern: zone1=black, zone2=pink
KS1001B-PAT-BLU,PUR     → 2-zone pattern: zone1=blue,  zone2=purple
KS1001B-PAT-BLU         → single color supplied: apply to all zones (or zone1 if the pattern is genuinely single-zone)
```
Same 3-letter color codes as Solid (`BLK`, `PNK`, `BLU`, `PUR`, `WHT`, `NVY`…) so there's one shared color vocabulary across Solid/Print/Pattern instead of three separate ones.
