The pattern-type SKU color resolver is currently hardcoded to specific
suffix strings (e.g. "BP" -> black+pink). This breaks for any new color
combination an admin adds - Blue+Purple, Blue+Black, a single color, etc.
- because each combo currently needs its own hardcoded case.

Refactor this to be generic:

1. Parse the SKU suffix after "-PAT-" as a comma-separated list of color
   tokens, e.g. "BLK,PNK" -> ["BLK", "PNK"], or "BLU" -> ["BLU"].

2. Resolve each token through the EXISTING color lookup table already
   used for solid-color SKUs (same hex/texture-asset map) - do not
   create a second color table.

3. Apply the resolved colors POSITIONALLY onto the pattern group's
   recolor zones (each GT pattern group already defines how many zones
   it has, e.g. GT014 = 2 zones). Token[0] -> zone[0], token[1] -> zone[1], etc.

4. If only ONE token is supplied but the pattern has multiple zones,
   apply that single color to ALL zones rather than throwing an error.

5. If the token count is greater than 1 and doesn't match the zone
   count, log a clear validation error naming the SKU and expected zone
   count - don't silently apply wrong colors or crash.

6. This must not require touching any code when a new color combination
   is added - it should be data-driven off the SKU string and the
   existing color table, the same way solid-color SKUs already work.

## 8. Supporting full color names, not just 3-letter codes
